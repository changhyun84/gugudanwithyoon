`기술설계서.md`는 **설계 의도**를, 이 문서는 **실제로 구현된 것과 그 과정에서 바뀐 결정**을 기록합니다.
둘이 어긋나는 부분은 이 문서가 최신입니다.

마지막 갱신: 2026-08-19 — 캐릭터 넷 다시 그림(11장), 확장 6A~6D 계획(9장), 결정 변경 2건(10·12장)

## 2. 설계서와 달라진 결정

새 대화에서 이어받을 때 **가장 먼저 읽어야 할 부분**입니다. 모두 이유가 있어서 바꾼 것이니 되돌리지 마세요.

### 2.1 쉬운 문제는 마스터로 세지 않는다

자신감용 2·5·9단 24개는 `m=2`에서 시작해 두 번만 맞히면 마스터가 됩니다. 그대로 두면 별이 첫 주에 24개 쌓여 캐릭터가 한꺼번에 열립니다.

→ `engine.js`의 `isRewardable(key)`가 판정합니다. 마스터리는 정상적으로 오르되 **별·스티커·`totals.mastered`에서 제외**됩니다. 판정은 `applyResult()` 안 한 곳에만 있습니다.

### 2.2 글자 정답의 오답은 같은 묶음에서 뽑는다

설계서 5.3은 숫자 정답만 다룹니다. 글자 정답은 규칙으로 만들 수 없어 **같은 `묶음`의 다른 정답**을 보기로 씁니다. 같은 묶음에 문제가 4개 미만이면 그 문제는 빠지고 부모 화면에 경고가 뜹니다.

→ 부모가 문제를 만들 때 묶음이 오답 품질을 결정합니다. `문제-만들기-안내.md`에 굵게 적혀 있습니다.

### 2.3 오답 생성 세부 규칙

- 답이 10 미만이면 ±1, ±2만 씁니다. 자릿수 바꿈(3→30)은 티가 너무 납니다
- **문제에 이미 등장하는 숫자는 보기에서 제외**합니다 (`6 ÷ 2`의 보기에 6이나 2가 나오면 안 됨)
- 나눗셈은 힌트를 자동 생성합니다 → "곱셈으로 바꿔봐. 2 × ? = 6"

### 2.4 조사 자동 보정

응원 메시지의 `{정답}` 치환 후 받침에 맞춰 조사를 고칩니다. "12이구나" → "12구나", "18야" → "18이야".

→ `app.js`의 `hasFinal()` / `fixJosa()`. 숫자는 읽는 소리 기준이며 받침 있는 끝자리는 **0·1·3·6·7·8**입니다(영·일·삼·육·칠·팔·십). 부모가 메시지를 쓸 때 조사를 신경 쓰지 않아도 됩니다.

### 2.5 v1 이관은 자동이 아니라 붙여넣기

설계서 10장은 `localStorage` 자동 변환을 전제하지만, v1이 다른 주소에서 돌던 파일이라 브라우저가 그 저장소를 읽지 못합니다.

→ v1의 `설정 → 기록 백업` 글자를 복사해 `/parent`에 붙여넣습니다. 변환 코드는 `parent.html`의 `fromV1()`.

### 2.6 친구들은 홈에서 발견된다

4단계 직후 캐릭터를 옷장 두 번째 탭에만 넣었더니 아이가 존재 자체를 몰랐습니다.

→ 목장에 **다음 친구를 회색 실루엣**으로 세우고 "별 8개를 모으면 고양이를 만날 수 있어"를 띄웁니다. 별이 충분하면 홈에 노란 버튼이 하나 더 생깁니다. 친구들은 독립 화면(`view === 'friends'`)이고, 옷장은 입히기만 남았습니다.

### 2.7 출제 후보가 8개는 되도록 보장한다

설계서 7.2의 "앞에서 3개만"을 그대로 적용하니, 팩 하나를 골랐을 때 후보가 3개뿐이라 20문제 중 같은 문제가 8번까지 나왔습니다.

v1에서 이 규칙이 잘 통한 이유는 쉬운 문제 24개가 늘 섞여 있었기 때문입니다. **3은 새로 배우는 것의 개수였지 출제 풀 크기가 아니었습니다.** 팩 필터가 그 완충을 없앴습니다.

→ `engine.js`: `NEW_AT_ONCE = 3`은 그대로 두고, 필터를 적용한 뒤 후보가 `MIN_POOL = 8`에 못 미치면 다음 문제를 순서대로 미리 엽니다. 구구단이나 "다 섞어서"에서는 후보가 이미 충분해 창이 3으로 유지됩니다 — v1 동작 그대로입니다.

추가로 **최근 3문제는 출제에서 제외**합니다(그러면 낼 게 없어지는 경우에만 직전 문제만 제외).

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 다 섞어서 | 19종 / 최다 2번 | 19종 / 최다 2번 |
| 팩 하나 선택 | **3종 / 최다 8번** | 8종 / 최다 4번 |

### 2.8 아이템은 앵커로 붙인다 — 배율까지 (2026-08-19 갱신)

아이템 SVG는 **양 기준 좌표 한 벌**만 있습니다(모자 100,30 / 목 100,96). 캐릭터마다 앵커점으로 옮기고, **앵커점을 중심으로 배율만큼 키웁니다.**

```js
anchor: { hat: [100, 46, 1.28], neck: [100, 111, 1.26] }   // 세 번째 값이 배율, 없으면 1
```

배율은 넷을 다시 그리면서(11장) 생겼습니다. 머리를 키웠더니 같은 왕관이 챙 없는 모자처럼 보였습니다.

`place()`가 `translate(앵커) scale(배율) translate(-양기준)` 한 줄로 처리합니다. **순서를 바꾸면 원점 기준으로 커져서 아이템이 화면 밖으로 날아갑니다.**

→ 새 캐릭터를 추가할 때 아이템 코드는 건드리지 말고 `CHARACTERS`에 앵커 세 값만 넣으세요.
→ 양은 배율이 없어 v1과 픽셀 단위로 같습니다.

### 2.9 끄기는 회수하지 않는다 (5A)

부모가 문제를 꺼도 **앞으로 출제되지 않을 뿐**입니다. 다음은 전부 유지합니다.

`facts`의 진도 · 이미 받은 별 · 도감 스티커 · `totals.mastered` · 해금한 캐릭터 · 열린 상점 단계

마스터한 문제를 끌 때 `totals.mastered`를 다시 계산하면 값이 줄고 → 상점 단계가 닫히고 →
**아이 화면에서 어제까지 살 수 있던 물건이 사라집니다.** 원칙 2.1(차감 금지)에 정면으로 걸립니다.

→ `app.js`는 `P.totals.mastered++`로 누적만 합니다. `facts`에서 재계산하는 코드를 만들지 마세요.
(`parent.html`의 `fromV1()`만 예외 — v1 이관은 어차피 덮어쓰기입니다.)

### 2.10 제외 필터는 `buildIndex()`에서 건다 (5A)

`engine.js`의 `buildIndex(packs, disabled)`가 색인을 지을 때 꺼진 것을 빼버립니다.
그 뒤의 `openKeys` · `poolSize` · `pickKey`는 **손대지 않았습니다.** 2.7의 `MIN_POOL = 8` 보정이
줄어든 문제 수 안에서 그대로 동작합니다. 엔진 입장에서는 "원래 그만큼인 팩"입니다.

부모가 실수로 전부 끄면 아이 화면이 빈 채로 멈추므로, 색인이 비면 **제외를 무시하고 다시 짓습니다.**

> 설계 검토 때는 서버에서 거르려 했지만, 오답 보기가 `packs.py`에서 이미 만들어져 오기 때문에
> 클라이언트에서 걸러도 오답 품질이 나빠지지 않습니다. 묶음(`묶음`)도 클라이언트로 오지 않습니다.
> 그래서 `server.py`·`packs.py`를 한 줄도 고치지 않았습니다.

### 2.11 제외 목록은 프로필 안에 둔다 (5A)

`data/settings.json`이 아니라 프로필 JSON의 `disabled` 필드입니다.

- 기존 `PUT /api/profile/{id}`를 그대로 써서 **서버 변경이 0**입니다
- 원자적 저장과 하루 1회 백업이 공짜로 따라옵니다
- 형제자매마다 다른 목록을 갖습니다 (학년이 다르면 이게 맞습니다)

부모 화면은 저장 직전에 프로필을 다시 받아 `disabled`만 얹고 PUT합니다.
아이가 놀고 있는 중이라도 진행이 덮이지 않게 하려는 것입니다.

### 2.12 `isRewardable`이 없어서 부모 화면이 죽어 있었다 (5A에서 고침)

`parent.html`이 `import { isRewardable } from '/engine.js'`를 하는데 `engine.js`에 그 export가
없었습니다. ES 모듈은 링크 단계에서 실패하므로 **부모 화면 스크립트 전체가 실행되지 않았습니다.**

→ `engine.js`에 `isRewardable(key)`를 추가했습니다. 2.1의 판정을 함수로 노출한 것이고,
`applyResult()` 안의 `entry.rewardable`과 같은 뜻입니다.

## 3. 실제 데이터 스키마

설계서 4.1에서 **추가된 필드**만 적습니다.

```jsonc
"daily": { "day": "2026-08-18", "solved": 0, "goal": 20, "speedRuns": 0,
           "right": 0, "grass": 0, "star": 0 },   // right·grass·star 추가
"history": [ { "day": "...", "solved": 20, "right": 17, "grass": 108, "star": 1 } ],

// 5A에서 추가 — 부모가 끈 것. 아이가 처음 들어올 때 없으면 빈 값으로 만들어집니다
"disabled": { "problems": ["나눗셈:q7"], "packs": ["3학년-분수"] },

// 5A에서 추가 — 문제마다 최근 결과. 최신이 앞, 최대 10개, 14일 지나면 버림
"facts": {
  "gugudan:7x8": { "m": 1, "seen": 9, "right": 3,
                   "log": ["0819:x", "0818:h", "0817:o"] }
  //  x 오답  /  h 힌트 쓰고 정답  /  o 혼자 정답
}
```

`seen`·`right`는 누적값이라 "요즘 어려워하는 문제"를 못 뽑습니다. 그래서 창(window)이 있는
`log`를 따로 답니다. `MMDD`에 연도가 없으므로 **오늘보다 미래로 읽히면 작년으로 봅니다** —
이 보정을 빼면 12월 31일에 1월 기록을 내년으로 보고 영영 안 지웁니다.

날짜가 바뀌면 `rollDay()`가 어제 `daily`를 `history`에 넣고(최근 90일) 초기화합니다.

문제 키는 `{팩id}:{공백 제거한 문제 텍스트}`입니다. 내장 구구단만 `gugudan:3x4` 형식입니다.

## 4. 실제 API

| 메서드 | 경로 | 비고 |
|---|---|---|
| GET | `/api/bootstrap` | 프로필 목록 + 설정 + 팩 메타 + **메시지** |
| GET | `/api/pack/{id}` | 팩 하나의 문제 전체 |
| GET | `/api/profile/{id}` | |
| PUT | `/api/profile/{id}` | |
| POST | `/api/profile/{id}` | **sendBeacon용** — PUT을 못 보내서 열어둠 |
| POST | `/api/profile` | 새 프로필 |
| GET | `/api/parent/packs` | 팩 목록 + 파싱 경고 + 메시지 경고 (PIN) |
| PUT | `/api/parent/settings` | (PIN) |

**API는 5A에서 하나도 늘지 않았습니다.** 부모 화면이 기존 엔드포인트만으로 다 합니다.

| 부모 화면이 필요한 것 | 어디서 |
|---|---|
| 전체 문제 목록 | `/api/bootstrap` + `/api/pack/{id}` → `buildIndex()` |
| 아이 진도·최근 기록 | `/api/profile/{id}`의 `facts` |
| 최근 7일 | 같은 프로필의 `history` + `daily` |
| 제외 목록 저장 | `PUT /api/profile/{id}` |

`/api/parent/summary`는 만들지 않았고, 앞으로도 필요 없습니다.

## 6. 검증 방법

브라우저 없이 실제 플레이를 돌려볼 수 있습니다. `jsdom`으로 DOM을 만들고 `app.js`를 그대로 import한 뒤 버튼을 클릭시키는 방식입니다.

```js
const dom = new JSDOM('<div class="wrap" id="app"></div><div class="toast" id="toast"></div>',
  { url: 'http://127.0.0.1:8770/', runScripts: 'outside-only', pretendToBeVisual: true });
// window.fetch를 서버로 연결하고 globalThis에 document/localStorage/navigator 주입
await import('./web/app.js?v=' + Date.now());
app.querySelector('#play').click();
```

지금까지 이 방식으로 잡은 것: 별 조기 고갈, 조사 오류, 한 자리 답의 부자연스러운 오답,
캐릭터 발견 경로 없음, **부모 화면이 통째로 죽어 있던 것**(2.12).

> ⚠️ **`test/`에는 지금 `t_book.mjs`(도감, 30개)만 있습니다.** 아래 둘은 5A 작업 중에 돌던 것인데

## 9. 확장(6A~6D) 검토 결과

### 9.1 좋은 소식 — 바꿀 곳이 생각보다 적습니다

| | 손댈 곳 |
|---|---|
| 단답형 | `packs.py`(유형 열) · `app.js`(입력 화면) · `engine.js`(채점 함수). **`server.py` 0줄** |

| 서술형 | 위 + `app.js`(쓰기 화면) · 스키마 `writings` |

특히 다음 셋이 이미 맞게 만들어져 있어 그대로 씁니다.

### 9.2 지금 코드에서 실제로 걸리는 곳

**`build_problems()`가 보기를 못 만들면 문제를 통째로 버립니다.**

```python
if len(choices) < 3:
    warnings.append(...)
    continue          # ← 여기
```

단답형에는 이럴 이유가 없습니다. 유형이 `short`면 보기 없이 싣고 「보기 보여줘」 버튼만 감춥니다. 서술형은 아예 보기를 만들지 않습니다.

**`parse_csv()`가 정답 없는 줄을 버립니다.**

```python
if not question or not answer:   # 서술형은 정답이 없어도 됨
```

여기를 놓치면 **서술형 문제가 전부 경고로 사라집니다.** 6C에서 제일 먼저 확인할 곳입니다.

**`renderQuiz()`는 `q.choices`가 있다고 가정합니다.** 유형 분기를 넣을 때 `topbar` · `qhead` · `bubble` · `feedback`은 그대로 재사용하고 **가운데 답하는 부분만** 갈아 끼우세요. 이 함수가 지금도 큰 편이라, 유형별로 통째로 복사하면 세 벌이 됩니다.

**`answer(picked)`가 `b.textContent`로 값을 읽습니다.**

```js
app.querySelectorAll('[data-pick]').forEach(b => b.onclick = () => answer(b.textContent));
```

입력창에서 부를 때는 `data-pick`이 없습니다. `answer(value)`로 값을 직접 넘기는 형태는 이미 되어 있으니, **입력 경로도 같은 함수를 부르게** 하세요. 채점·보상·저장·마스터리가 전부 여기 모여 있어서, 두 번째 경로를 만들면 그때부터 어긋납니다.

## 10. 결정 변경 기록 — AI가 조언을 합니다 (2026-08-19)

이 문서에서 **원칙이 완화된 유일한 사례**입니다. 되돌리기 전에 여기를 읽으세요.

### 10.1 무엇이 바뀌었나

처음 설계한 원칙 2.10은 **AI가 조언을 일절 못 하게** 했습니다. 반응만 하고, 빠진 것이 있어도 정보로만 흘리고, 가르치지 않는 구조였습니다. 어른의 지적이 아이를 다시 조용하게 만들까 봐서였습니다.

부모가 근거를 가지고 뒤집었습니다.

> 아이가 자신감이 붙었습니다. 그리고 **부모의 지적은 부끄러워하지만, 선생님의 지시는 기꺼이 따르고 오히려 안정감을 얻습니다.**

이건 이 아이에 대한 직접 관찰이고, 문서상의 설계보다 강한 근거입니다.

### 10.2 왜 이 완화가 원칙을 안 깨나

핵심은 **누가 말하느냐**입니다. 같은 문장도 부모가 말하면 지적이 되고 선생님이 말하면 배움이 됩니다. 아이가 이미 그 구분을 가지고 있습니다.

그래서 완화한 것은 "조언 금지" 하나뿐이고, **아래 셋이 그대로라서 성립합니다.**

| 그대로인 것 | 왜 이게 조언을 안전하게 만드나 |
|---|---|
| 서술형에 점수·마스터리·별이 없음 | 선생님 말이 보상에 **영향을 줄 수 없음**. 아이 입장에서 조언은 *잃을 것이 없는 정보* |
| 보상이 조언보다 **먼저** 지급됨 | 이미 받은 다음에 듣는 말이라 판정으로 읽히지 않음 |
| 선생님이 친구들과 **분리**됨 | "어른도 헷갈린다"(2.9)를 보여주는 다섯은 그대로 남음 |

**채점과 조언을 같이 붙이면 조언이 감점 사유로 읽힙니다.** 이 셋 중 하나라도 무너지면 조언을 다시 막아야 합니다.

### 10.3 되돌리는 순서

관찰이 근거이므로 관찰이 바뀌면 되돌립니다. 한 번에 다 끄지 말고 순서대로.

```
1. 조언 스위치 끄기        선생님은 남고 말만 짧아짐 — 아이는 거의 못 느낌
2. AI 끄기                 선생님이 준비된 문장만 말함
3. 서술형 자체를 끄기       마지막 수단
```

되돌릴 신호는 **서술형 글자 수**입니다. 조언을 켠 뒤 아이가 쓰는 양이 줄면 선생님 말이 지적으로 읽히고 있다는 뜻입니다. `writings`에 날짜와 글이 다 있으니 세어볼 수 있습니다.

세션 이탈이나 서술형 회피가 보이면 그때는 이미 늦은 편입니다. 글자 수가 먼저 움직입니다.

| `data/settings.json` | `ai.advice`, `ai.teacherName` |
| `parent.html` | 조언 스위치, **조언 문장만 모아 보는 목록** |

선생님 SVG는 앵커를 안 넣습니다. 아이템을 못 입히는 것이 의도입니다 — 꾸밀 수 있으면 목장 식구가 되고, 목장 식구가 되면 역할이 섞입니다(기획서 4.3).

### 10.5 남은 위험

**금지어 목록으로는 못 막습니다.** `BANNED`를 피해 가는 지적 문장은 얼마든지 만들어집니다 — "이 부분은 조금 더 생각해보면 좋겠어" 같은 것. 검열은 최후의 그물이고, **진짜 확인은 부모가 로그의 조언 문장을 읽는 것**입니다. 그래서 부모 화면의 조언 목록이 선택 기능이 아닙니다.

**모델이 바뀌면 말투가 바뀝니다.** `ai.model`을 고친 다음에는 조언 문장 열 줄을 반드시 읽어보세요. 같은 프롬프트가 모델에 따라 훨씬 훈계조로 나올 수 있습니다.

**친구 캐릭터가 오염될 수 있습니다.** 선생님 대사를 쓰다 보면 `messages.csv`의 친구 대사도 가르치는 톤으로 흘러갑니다. 친구들은 끝까지 **"나도 이거 자꾸 헷갈리더라"** 쪽이어야 합니다. v1이 통한 이유가 그것뿐입니다.

## 11. 캐릭터를 다시 그렸습니다 (2026-08-19)

**코드가 실제로 바뀐 유일한 항목입니다.** 위 9·10장은 계획이지만 이건 `web/characters.js`에 반영돼 있습니다.

### 11.1 무엇이 문제였나

부모 관찰: **"양을 제외한 캐릭터들의 미형이 너무 부족하다."**

원인은 그림 실력이 아니라 **호환을 위해 그림체를 맞춘 것**이었습니다. 넷 다 `ellipse cx=100 cy=112 rx=46 ry=40` 몸통에 같은 `legs()`, 같은 `eyes()`를 쓰고 색만 달랐습니다. 아이템 앵커가 위치만 옮길 수 있어서 머리 크기를 캐릭터마다 다르게 할 수 없었고, 그래서 다 비슷한 체형이 됐습니다.

### 11.2 배율이 제약을 풀었습니다

앵커에 세 번째 값(배율)을 더하니 **그림체를 자유롭게 하면서 아이템 한 벌을 계속 공용으로 쓸 수 있게** 됐습니다(2.8). 아이템 SVG는 한 글자도 안 고쳤습니다.

### 11.3 넷에 적용한 비례

| | 이전 | 지금 |
|---|---|---|
| 얼굴 `rx` | 34~37 | **40~41** |
| 몸통 `rx` | 46 | 36~40 |
| 눈 반지름 | 5.6 | **9** |
| 눈 위치 | 얼굴 한가운데 | **얼굴 아래쪽 1/3** |
| 하이라이트 | 1개 | **2개** (큰 것 + 작은 것) |
| 다리 | `rect` 4개 | **앞발 2개** |

**눈을 얼굴 아래로 내린 것이 가장 큰 차이**입니다. 아기 얼굴의 핵심 비례이고, 이것만 고쳐도 인상이 달라집니다.

### 11.4 정체성은 비례보다 우선합니다

- 카피바라의 네모난 얼굴은 모서리 `rx`만 31로 굴리고 유지했습니다. 둥글게 만들면 귀여워지지만 **카피바라가 아니게 됩니다**
- 고양이 꼬리는 굵은 선 두 겹(테두리색 15 + 몸색 11)으로 말아 올렸습니다
- 토끼 앞니는 턱선 아래로 2px 삐져나옵니다. 의도한 것입니다
- 코알라의 `z z`는 평소 얼굴일 때만 나옵니다

## 13. 5B 착수 전 시뮬레이션 (2026-08-19)

`node sim/60days.mjs`를 돌린 결과입니다. **5B는 전부 보상 규칙이라 이 숫자가 곧 설계값입니다.**

|---|---|---|---|---|---|---|---|

| 45 | 48 | 78 | 1 | 5 | 6 | 4,425 | 875 |

### 13.1 발견 1 — 상점 5단계가 도달 불가능했습니다

조건이 **80문제 마스터**인데 별을 주는 문제가 **75개뿐**입니다. 부모가 팩을 더 넣지 않으면 영영 안 열립니다.

→ **65로 내렸습니다**(기획서 8.3). 시뮬레이션에서 68일쯤 열립니다.

조건은 **내리는 것만 안전**합니다. 올리면 이미 열린 단계가 닫히고, 어제까지 살 수 있던 물건이 사라집니다(원칙 2.1). 팩이 늘어도 65는 계속 도달 가능합니다.

### 13.2 발견 2 — 별 소비처가 50일쯤 마릅니다

친구 4명 해금(88) + 배경 6종(49) = **137**을 다 쓰고 나면 살 것이 없습니다. 20회 반복에서 평균 **50일**(42~54일), 스크립트 기본 실행에서 53일이었습니다.

문서 8장이 "55~60일"로 예상했는데 **더 빠릅니다.** 90일에는 별 60이 그냥 쌓여 있습니다.

| 대책 | 효과 |
|---|---|
| 배경 5~8종 → **10종 이상** | 며칠 미룸. 결국 마름 |
| **소원권** | 고갈되지 않는 유일한 소비처 |

→ **소원권은 5B의 마지막 항목이 아니라 필수 항목입니다.** 배경만 넣고 끝내면 두 달 뒤 별이 의미를 잃습니다.

### 13.3 발견 3 — 이야기 판(6C)은 이 문제를 악화시킵니다

서술형 하루 2문제로 이야기 판을 채우면 별 소비처가 마르는 날이 **53일 → 41일**로 당겨집니다. 90일 별 잔고는 60 → **105**입니다.

→ **소원권을 먼저 넣고 6C를 하세요.** 순서를 바꾸면 별이 남아도는 상태로 6C를 얹게 됩니다.

### 13.4 발견 4 — 풀은 괜찮습니다

60일에 6,066을 벌어 잔고 416, 90일에 9,427을 벌어 잔고 777입니다. **계속 증가하지 않습니다.** 7장의 "풀이 남는다"는 전용 아이템 15개(12장)로 해결됐습니다.

단, 3~5단계 전용 아이템은 **해금한 친구 수만큼만** 살 수 있어서, 친구가 늦게 열리면 풀이 그만큼 더 남습니다. 시뮬레이션은 그것까지 반영한 값입니다.

### 13.5 그래서 5B 순서를 이렇게 바꿉니다

```

5. 소원권             ← 4번과 묶어서. 미루면 두 달 뒤 별이 죽습니다
6. 용돈               🌿 풀. 주 1회 정해진 요일에만
```

**4번과 5번을 같이** 하는 것이 이번 시뮬레이션의 결론입니다. 원래 소원권은 5B의 맨 끝이었습니다.

## 14. 도감 화면 (5B-1, 2026-08-19 완료)

`collection.stickers`에 값만 쌓이고 보여주는 곳이 없던 것을 채웠습니다(7장).

### 14.1 무엇이 생겼나

- 홈에 **도감** 버튼 (`view === 'book'`). 버튼이 넷이 되어 2×2로 나눴습니다
- 12칸 판. **채우는 중인 판이 맨 위**, 다 채운 판은 아래에 최신순
- 판을 채우면 **별 3** — 기획서 8.4

### 14.2 스티커는 문제마다 색과 기울기가 고정입니다

`hashOf(key)`로 색 6종 중 하나와 −3~+3도 기울기를 정합니다. 무작위로 하면 화면을 다시 열 때마다 스티커가 바뀌어서 **모은 것이 아니라 그때그때 그려지는 것처럼** 보입니다.

라벨은 8자 이하로 맞춥니다. 구구단은 `7×8`, 짧은 문제는 문제 그대로, 긴 문제는 **정답**을, 둘 다 길면 잘라서 `…`.

### 14.3 판 보상은 더하기만 합니다 — `catchUpBoards()`

```js
const done = Math.floor(stickers.length / BOARD_SIZE);
const due  = done - (boardsCompleted || 0);
if (due <= 0) return 0;          // ← 줄어드는 경로가 없다
```

한 함수를 **두 곳**에서 씁니다.

| 어디 | 왜 |
|---|---|
| `answer()`의 마스터 직후 | 판을 채운 그 순간에 별 3 |
| `enter()`의 프로필 진입 | **5B 이전에 모아둔 스티커를 소급** |

소급이 필요한 이유: 도감 보상은 지금 생겼는데 스티커는 4단계부터 쌓이고 있었습니다. 37장을 모아둔 아이는 들어오는 순간 별 9를 받습니다.

`boardsCompleted`가 스티커 수보다 앞서 있어도 **줄이지 않습니다.** `due <= 0`이면 그냥 0입니다(원칙 2.9).

### 14.4 부모가 끈 문제의 스티커도 보입니다

`stickerLabel()`은 `INDEX`에 없는 키도 읽습니다. 키가 `{팩id}:{공백 뺀 문제}`라 뒤쪽을 그대로 쓰면 됩니다. 구구단은 `gugudan:(\d+)x(\d+)`를 정규식으로 풀어 `7×8`로 만듭니다.

**이게 없으면 부모가 문제를 끄는 순간 아이 도감에 구멍이 생깁니다.** 원칙 2.9가 화면에서 깨지는 자리입니다.

### 14.5 토스트는 하나만

마스터 토스트와 판 완성 토스트가 겹칩니다. 정답이면 1.1초 뒤 다음 문제로 넘어가는데 토스트는 1.8초라 두 개를 띄우면 뒤엣것이 잘립니다.

→ 판을 채운 날은 **판 완성 쪽만** 띄웁니다. 더 큰 소식이 이깁니다.

### 14.6 검증

```
node test/t_book.mjs        # 30개
```

`jsdom`이 없어서 순수 함수 네 개(`catchUpBoards`·`stickerLabel`·`hashOf`·`boardHTML`)를 `app.js`에서 정규식으로 떼어 검사합니다. **5B의 나머지도 같은 방식으로 붙이세요** — 보상 로직은 대부분 순수 함수라 DOM 없이 검사됩니다.

특히 이 셋을 봅니다.

- 12장에 별 3, 재호출해도 다시 안 줌
- `boardsCompleted`가 앞서 있을 때 **줄지 않음**
- 색인에 없는 키도 라벨이 나옴

함수 이름을 바꾸면 `grab()`이 "app.js에 …가 없습니다"로 바로 실패합니다. 조용히 통과하지 않습니다.

`node sim/60days.mjs`도 다시 돌렸습니다. 도감 보상은 시뮬레이션이 이미 반영하고 있던 값이라 균형은 그대로입니다(별 소비처 51일에 마름 — 13.2).

## 15. 상점 단계 개방과 전용 아이템 (5B-2, 2026-08-19 완료)

기획서 8.3·8.7의 구현입니다. 아이템이 13종 → **30종**, 총액 2,430 → **9,450풀**이 됐습니다.

### 15.1 무엇이 생겼나

| | |
|---|---|
| `tier` · `only` | 아이템 정의에 두 필드. **둘 다 없을 때가 기본**이라 기존 13종은 한 줄도 안 고쳤습니다 |
| `slotOf(id)` | 슬롯 판정을 한 곳으로. `isHat(id) ? 'hat' : 'neck'`이 세 갈래가 됐습니다 |
| `prop` 슬롯 | 스키마에만 있던 것을 실제로 씁니다. 앵커도 캐릭터마다 새로 넣었습니다 |
| 전용 15종 | 캐릭터당 모자·목도리·소품 하나씩 |
| 공용 소품 2종 | 풍선·그림책 (2단계) |
| `catchUpTier()` | `totals.mastered` → `shopTier`. **올리기만 합니다** |

### 15.2 단계는 내려가지 않습니다

```js
const now = Math.max(before, tierOf(P.totals.mastered));
```

`Math.max`가 전부입니다. `totals.mastered`는 누적만 하지만(2.9), 혹시 줄어드는 경로가 생겨도 **선반은 안 닫힙니다.** 닫히면 어제까지 살 수 있던 물건이 사라집니다.

`P.settings.newTier`에 새로 열린 단계를 적어두고 홈에 알림 버튼을 띄웁니다. 가게에 들어가면 지웁니다. 서버·스키마 변경은 없습니다 — `settings`는 이미 있는 객체입니다.

### 15.3 아직 못 만난 친구의 전용은 가게에 안 보입니다

```js
const buyable = it => (it.tier || 1) <= P.shopTier &&
                      (!it.only || P.characters.unlocked.includes(it.only));
```

다음 목표를 보여주는 일은 목장의 회색 실루엣이 이미 하고 있습니다(2.6). 두 곳에서 같은 일을 하면 **가게가 잠긴 물건 창고**가 되고, 살 수 없는 것이 살 수 있는 것보다 많아집니다.

덕분에 **두 화폐가 서로를 밉니다** — 별로 친구를 만나면 풀 쓸 곳이 세 개씩 늘어납니다. 지금까지 풀과 별은 서로 무관했는데 여기서 처음 맞물립니다.

### 15.4 옷장에서 안 보이는 것은 사라진 게 아닙니다

토끼 리본은 토끼일 때만 목록에 뜹니다. 아이가 헷갈리지 않게:

- 가게에서 전용은 **그 친구에게 씌워서** 보여주고 이름표(*"토끼만"*)를 붙입니다
- 사면 **주인에게 바로 입혀둡니다** — `worn(it.only || active())`
- 다른 친구 전용만 가진 상태면 옷장이 *"다른 친구한테 가보면 있을지도!"* 라고 알려줍니다

### 15.5 소품 앵커는 몸 옆입니다

양 기준 `[148, 146]`. 모자·목도리와 달리 **몸 위에 겹치므로 마지막에 그립니다.**

토끼는 꼬리가 그 자리에 있어 앵커를 아래로(`[150, 157]`) 내렸습니다. 겹침이 남아 있을 수 있으니 눈으로 보세요.

### 15.6 검증

```
node test/t_book.mjs     # 30개

```

**시뮬레이션이 이제 `characters.js`에서 가격표를 직접 읽습니다.** 가격을 두 곳에 두면 반드시 어긋납니다.

`t_shop.mjs`가 실제로 사고를 하나 잡았습니다 — **아이템 30종이 데이터만 있고 그림이 하나도 없는 상태**로 전 조합 렌더링을 통과했습니다. 빈 문자열도 유효한 SVG라서요. 그래서 *"아이템을 씌운 SVG가 안 씌운 것보다 길어야 한다"* 는 검사를 넣었습니다. 정의만 있고 그림이 없으면 **화면에는 아무 일도 안 일어나면서 풀만 빠져나갑니다.**

### 15.7 시뮬레이션 결과 — 두 목표값 통과

시뮬레이션에도 버그가 있었습니다. 캐릭터 값을 **차액**(8·7·10·15 = 40)으로 계산했는데 실제 `pickChar()`는 매번 **전액**을 뺍니다(8+15+25+40 = 88). 별 소비가 절반으로 잡혀 낙관적으로 나오고 있었습니다.

| 친구 | 4 / 5 |
| 풀 잔고 | 1,471 — 계속 증가하지 않음 ✓ |
| 산 것 | **27 / 30** |

90일에 아직 살 것이 3개 남습니다(카피바라 전용 — 아직 못 만남). 성공 기준 2번 "8주가 지나도 살 게 없다는 상태가 오지 않는다"를 넘겼습니다.

## 16. 배경과 소원권 (5B-3, 2026-08-19 완료)

13.2에서 확인한 **별 소비처 고갈**을 막는 작업입니다. 둘을 같이 넣은 이유가 16.4에 있습니다.

### 16.1 배경 — `web/backgrounds.js` (새 파일)

11종(무료 1 + 별 10, 합계 **83별**). 가게에 `배경` 탭이 생겼습니다.

배경은 **CSS 변수 세 개만** 바꿉니다.

```
--meadow       하늘 쪽 (위)
--meadow-deep  땅 쪽 (아래)
--onpage       카드 바깥 글자색   ← 새로 만든 것
```

`--onpage`가 핵심입니다. 밤 배경을 넣으려면 페이지가 어두워지는데, 그러면 카드 **바깥** 글자가 안 보입니다. 그래서 `body{color}`를 `--onpage`로 돌리고 `.card`·`.item`·`.says p`에 `color:var(--ink)`를 못 박았습니다. **카드 안은 어떤 배경에서도 그대로**입니다.

무료 배경(`day`)은 계절·시간에 따라 저절로 바뀝니다(기획서 8.5) — 한밤·이른 아침·해질녘·밤, 그리고 낮은 봄·여름·가을·겨울. 아무것도 안 사도 화면이 늘 같지는 않습니다. `render()`마다 다시 계산하므로 놀다가 저녁이 되면 화면이 넘어갑니다.

장식(별·눈·꽃잎·비·오로라·반딧불)은 `#sky` 고정 레이어에 SVG로 얹습니다. **무작위가 아니라 고정 배치**입니다 — 화면을 다시 열 때마다 별자리가 바뀌면 산만합니다.

### 16.2 소원권 — `content/wishes.csv`

문제 팩·메시지와 **같은 방식**입니다. 파일이 없으면 기능 자체가 아이 화면에 안 나타납니다. 그게 기획서 8장이 말한 "기본 꺼짐"입니다 — 따로 스위치를 만들지 않았습니다.

```csv
소원,별,설명
아이스크림 사러 가기,8,아무 때나 쓸 수 있어
같이 영화 보기,20,팝콘도 같이
```

별 칸이 숫자가 아니면 **그 줄만** 건너뛰고 부모 화면에 경고가 뜹니다. 팩 파서와 같은 규칙입니다.

### 16.3 받은 소원권은 지우지 않습니다

`P.wishes`는 **받은 기록**이지 남은 장수가 아닙니다. "썼다" 표시를 만들지 않았습니다.

이유가 둘입니다.

1. 아이가 실수로 눌러 날릴 수 있고, **사라지는 것은 회수처럼 느껴집니다**(원칙 2.1)
2. 소원권은 관계형 보상입니다. 아이가 화면을 부모에게 보여주는 것이 이 기능의 전부이고, 들어준 뒤에 목록이 지워질 이유가 없습니다

같은 소원을 여러 번 바꿀 수 있습니다. 아이스크림을 두 번 바꾸면 아이스크림 두 개입니다.

부모 화면에 `소원권` 섹션이 생겼습니다 — 걸어둔 소원 목록, 아이가 몇 번 바꿔갔는지, 바꾼 날짜. 아이가 말을 안 해도 부모가 압니다.

### 16.4 시뮬레이션 — 소원권이 없으면 140일에 별이 죽습니다

시뮬레이션도 이제 `backgrounds.js`에서 배경 값을 직접 읽습니다. 가격표를 두 곳에 두지 않습니다.

## 17. 용돈 (5B-4, 2026-08-19 완료) — 5B 끝

16.5에서 나온 **180일 풀 잔고 10,309**을 받는 소비처입니다.

### 17.1 화폐는 풀입니다

| | 화폐 | 왜 |
|---|---|---|
| 소원권 | ⭐ 별 | 드물고 사건이어야 함 |
| 용돈 | 🌿 **풀** | 풀은 '푼 것'에 주므로 **틀려도 용돈이 나옵니다** |

별로 바꾸게 하면 별은 마스터(=정답)에만 붙으므로 **"틀리면 돈을 못 번다"** 가 됩니다. 이 게임이 통한 이유가 정확히 그 반대입니다.

`t_allow.mjs`가 `exchange()` 본문을 정규식으로 검사합니다 — `wallet.grass`를 빼고 `wallet.star`는 **건드리지 않는지**. 이게 이 기능의 유일한 절대 조건입니다.

### 17.2 설정은 `data/settings.json` (파일이 아니라)

소원권은 `content/wishes.csv`인데 용돈은 부모 화면 설정입니다. **실제 돈이라 PIN 뒤에 두는 편이 맞습니다.**

```jsonc
"allowance": { "on": false, "per": 100, "won": 200, "day": 6, "max": 500 }
```

기본값이면 토요일마다 **최대 1,000원**입니다(주 수입 약 700풀 중 500).

`public_settings()`에 `allowance`를 더했습니다. **화이트리스트 방식은 그대로 유지했습니다** — 전개(`**s`)로 바꾸면 나중에 AI 키가 들어오는 날 바로 새어 나갑니다.

### 17.3 상한이 두 소비처를 갈라놓습니다

풀은 **아이템과 용돈이 같이 씁니다.** 상한이 없으면 아이가 모은 풀을 전부 돈으로 바꿔버려서, 가게에 사고 싶은 게 있어도 못 삽니다.

`max`가 그 장치입니다. 그리고 아이가 100·300·500 중에 **고릅니다** — 자동으로 다 바꾸지 않습니다.

### 17.4 주 1회

`allowanceDay()`가 셋을 다 봅니다 — 켜져 있고, 오늘이 그 요일이고, **오늘 아직 안 바꿨을 때**. 요일이 고정이라 "그날 한 번"이 곧 "주 한 번"입니다.

매일 환전되면 임금이 되고, 임금이 되면 놀이가 노동이 됩니다(원칙 2.5).

### 17.5 기록은 지우지 않습니다

`P.allowance`는 **바꾼 기록**입니다. 소원권과 같은 규칙입니다. 부모 화면에 날짜·금액·합계가 나옵니다.

| **180일 풀 잔고** | **10,309** | **1,845** |

두 화폐 모두 180일에 살아 있습니다. **5B의 목표였던 "8주가 지나도 살 게 없다는 상태가 오지 않는다"(성공 기준 2)를 넘겼습니다.**

곁들여 나온 관찰 하나 — 용돈을 켜면 아이템 구매가 느려집니다(90일 기준 27/30 → 24/30). 풀 하나를 두 곳이 나눠 쓰니 당연하고, **어느 쪽을 고를지는 아이가 정합니다.** 그게 이 설계의 의도입니다.

## 18. 학습 진도 관리 검토 (2026-08-19) — 5C 제안

기획서 16장에 설계를, 기술설계서 5.7에 구현을 적었습니다. 여기는 **지금 코드에서 실제로 걸리는 것**만 적습니다.

### 18.1 지금 코드에서 바로 걸리는 것 두 개

**`sorted(folder.glob('*'))`가 문자열 정렬입니다.**

```
지금:      1-1 · 1-10 · 1-2 · 1-3 · 2-1
자연 정렬:  1-1 · 1-2 · 1-3 · 1-10 · 2-1
```

단원이 열 개를 넘는 순간 진도 순서가 뒤집힙니다. 그리고 순서는 **`engine.js`의 `order`로 이어져 출제 순서까지** 바꿉니다. 나중에 고칠 것이 아니라 처음부터 넣어야 합니다.

**`scan()`이 폴더를 안 내려갑니다.** `glob('*')`에 디렉터리도 걸리는데 `suffix` 검사에서 조용히 빠집니다. 부모가 폴더를 만들면 **아무 일도 안 일어납니다** — 오류도 안 납니다. 지금 이 상태가 제일 나쁩니다.

### 18.2 팩 id를 바꾸면 안 됩니다

`수학/1-1 구구단.csv`의 팩 id를 `수학-1-1-구구단`으로 만들고 싶은 유혹이 있습니다. **하지 마세요.**

문제 키가 `{팩id}:{문제}`라서, id가 바뀌면 **아이가 몇 달 쌓은 진도·마스터·스티커가 통째로 새 문제로 취급됩니다.** 파일을 폴더로 옮기는 것만으로 그렇게 됩니다.

→ id는 **파일명 슬러그만**. 과목은 별도 필드. 다른 폴더에 같은 파일명이 있을 때만 충돌이고, 그건 경고로 처리합니다.

### 18.3 `progress`와 `disabled`를 합치지 마세요

진도를 `disabled.packs`로만 표현하면 서버·엔진 변경이 0이라 매력적입니다. **하지만 안 됩니다.**

`disabled`는 "빼는 목록"이라, **뒤에 새 파일을 넣으면 목록에 없으니 바로 열립니다.** 다음 학기 분량을 미리 넣어두는 것이 이 기능의 존재 이유인데 그게 깨집니다.

`progress`는 "여기까지"라서 뒤에 뭐가 추가돼도 안 열립니다. 둘은 역할이 다르고 **둘 다 필요합니다.**

| | 뜻 | 되돌릴 수 있나 |
|---|---|---|
| `progress` | 학교 진도. 과목마다 "여기까지" | **예** (16.4) |
| `disabled` | "이 문제는 지금 빼자" | 예 (5A) |

### 18.4 진도는 내려도 됩니다 — 별·스티커와 다릅니다

지금까지 "내려가면 안 되는 것"이 셋이었습니다 — 상점 단계(12장), 도감 판(14장), 받은 소원권·용돈(16·17장). **진도는 그 셋과 다릅니다.**

내려가도 **사라지는 것이 없기 때문**입니다. 앞으로 그 문제가 안 나올 뿐, `facts`·별·스티커·해금·상점 단계는 전부 그대로입니다. 5A의 문제 켜고 끄기와 같은 규칙입니다(2.9).

부모 화면에 그 문장을 그대로 띄우세요 — 그게 없으면 부모가 진도를 못 내립니다.

### 18.5 아이 화면에 안 열린 단원을 보여주지 마세요

목장의 회색 실루엣(2.6)을 그대로 따라 하고 싶겠지만, **반대로 해야 합니다.**

| | 회색으로 보여주나 | 누가 여나 |
|---|---|---|
| 다음에 만날 친구 | 예 | **아이** — 별을 모아서 |
| 아직 안 배운 단원 | **아니오** | **학교** |

아이가 통제할 수 없는 것을 눈앞에 두면 목표가 아니라 압박입니다. 2.6이 잘 통한 이유는 그게 아이가 **여는** 것이었기 때문입니다.

### 18.6 별 페이싱을 다시 봐야 합니다

지금 별을 주는 문제가 **75개**입니다. 수학 4단원 + 한국사 4단원이면 **150~200개**가 됩니다. 마스터 보상(문제당 별 1)이 두세 배가 됩니다.

거기에 **단원 완주 보상 별 5**(기획서 8.2의 "팩 하나 전체 마스터")가 단원 단위로 훨씬 자주 터집니다. 지금은 팩이 커서 거의 안 나오는 보상인데, 단원은 15~24문제라 자주 나옵니다.

소원권(8.8)이 무한 소비처라 구조는 버팁니다. 그래도 **`node sim/60days.mjs 180`을 문제 파일을 늘린 뒤 다시 돌려야 합니다.** 시뮬레이션은 `content/problems`를 실제로 읽으므로, 파일만 넣으면 바로 새 숫자가 나옵니다.

한 가지 더 — `TIER_NEED`의 5단계 조건 **65문제**는 지금 75개 기준입니다. 문제가 150개가 되면 5단계가 너무 빨리 열립니다. **조건은 올리면 안 되므로**(원칙 2.1), 6단계를 뒤에 추가하는 방식으로 늘리세요.

### 18.7 작업 크기

| | |
|---|---|
| `packs.py` | 재귀 스캔 · 자연 정렬 · `subject`/`unit`/`order` 필드 |
| `engine.js` | `buildIndex(packs, disabled, progress)` — **세 번째 인자만** |
| `app.js` | 자유 모드 2단계, 새 단원 알림 |
| `parent.html` | 과목별 진도 드롭다운, 단원 목록, "다음 단원 열까요?" 제안 |
| `server.py` | **없음** — 팩 메타에 필드가 늘 뿐 |

`openKeys`·`poolSize`·`pickKey`는 **손대지 않습니다.** 5A에서 `disabled`를 넣을 때와 같습니다(2.10).

### 18.8 순서 제안 — 6A보다 먼저

**5C로 6A(단답형) 앞에 넣기를 권합니다.**

- 지금 실사용 중이고, 문제 파일이 늘어나는 순간 바로 필요합니다
- 6A가 먼저 들어가면 `유형` 열과 폴더 구조를 **같이** 옮겨야 해서 부모가 두 번 고칩니다
- 자연 정렬은 지금 **조용히 틀리고 있는 버그**입니다. 단원을 안 쓰더라도 고쳐야 합니다

```
5C-1  재귀 스캔 + 자연 정렬 + subject/unit 필드      아이 화면 변화 없음
5C-2  progress 필드 + buildIndex 세 번째 인자
5C-3  부모 화면 진도 드롭다운 + 다음 단원 제안
5C-4  아이 화면 — 자유 모드 2단계, 새 단원 알림
```

5C-1은 **아이 화면이 전혀 안 바뀌는** 작업이라 위험이 낮습니다. 5A·6B와 같은 성격입니다.

## 19. 재귀 스캔과 자연 정렬 (5C-1, 2026-08-19 완료)

18장의 첫 항목입니다. **아이 화면은 한 줄도 안 바뀌었습니다.**

### 19.1 고친 것

| | |
|---|---|
| `natural(name)` | 숫자 조각을 숫자로 비교. `1-10`이 `1-2` 뒤로 갑니다 |
| `scan()` | 폴더를 **한 단계** 내려갑니다. 폴더 이름이 과목 |
| `read_pack()` | `scan()`에서 떼어냈습니다. `subject`·`unit`·`order` 추가 |
| `server.py` | 팩 메타에 세 필드를 실어 보냅니다. **엔드포인트는 그대로** |
| `parent.html` | 팩 목록을 과목별로 묶어 보여줍니다 (읽기 전용) |

### 19.2 자연 정렬은 화면 순서가 아닙니다

```
지금까지:  1-1 · 1-10 · 1-2 · 1-3 · 2-1
고친 뒤:   1-1 · 1-2 · 1-3 · 1-10 · 2-1
```

이 순서가 `order`가 되고, `order`는 `engine.js`의 **"앞에서 3개씩 열기"**(7.2)로 이어집니다. 정렬이 틀리면 **엉뚱한 문제가 먼저 열립니다.** 단원을 안 쓰더라도 고쳐야 했던 이유입니다.

### 19.3 팩 id는 파일명 슬러그 그대로입니다

`수학/1-1 구구단.csv`의 id는 `1-1-구구단`입니다. **과목이 안 들어갑니다.**

id가 바뀌면 문제 키(`{팩id}:{문제}`)가 바뀌고, 아이가 쌓은 진도·마스터·스티커가 통째로 새 문제가 됩니다. 그래서 **파일을 폴더로 옮기는 것만으로는 아무것도 안 잃습니다** — 부모가 지금 구조를 안심하고 정리할 수 있어야 합니다.

`t_units.mjs`가 이걸 직접 봅니다 — 같은 파일을 폴더 밖과 폴더 안에서 스캔해 id가 같은지.

**대신 이름 충돌이 생깁니다.** 다른 폴더에 같은 파일명이 있으면 먼저 온 것만 싣고 경고를 답니다. 실제로는 `1-1 구구단.csv` 처럼 쓰므로 드뭅니다.

### 19.4 기존 파일은 그대로

폴더 밖의 파일은 `subject: null`, `unit: null`이고 **진도 관리 대상이 아닙니다.** 항상 열립니다.

저장소의 파일 3개(`과학-식물`·`나눗셈`·`한국사-옛날사람들`)는 한 글자도 안 고쳤고 그대로 읽힙니다. 옮길지 말지는 부모가 정합니다.

### 19.5 단원 번호

파일명이 숫자로 시작하면 그 부분이 단원입니다 — `1-1`, `2`, `3.1`. 없으면 `null`이고 진도 관리 대상이 아닙니다.

진도 비교는 **`unit` 문자열이 아니라 `order`로** 합니다(기술설계서 5.7). 그래서 부모가 `1-1`을 쓰든 `01`을 쓰든 순서만 맞으면 됩니다.

### 19.6 검증

```
node test/t_units.mjs     # 24개
```

파이썬으로 임시 폴더에 가짜 문제 파일을 만들어 `packs.scan()`을 돌립니다. 자연 정렬·과목 추출·단원 추출·이름 충돌·두 겹 폴더 무시, 그리고 **id가 안 바뀌는 것**.

마지막 두 검사는 **저장소의 실제 파일**을 읽습니다 — 3개가 그대로 읽히고 전부 과목 없음인지.
